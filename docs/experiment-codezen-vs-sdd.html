Experiment runbook: CodeZen vs SDD vs clean baseline (superseded)

Two repository-carried engineering methods, measured against each other and against no methodology at all, on the one task axis both of them claim — with a control axis to price their overhead. 4 conditions × 2 agents = 8 cells.

1. What this experiment is (retired design)

Question
Does a repository's agent configuration change measured performance — and do two methods making different claims separate from each other?
Conditions
baseline, sdd, codezen-full, codezen-viable (§3).
Agents
claude-code / claude-sonnet-5 and codex / gpt-5.6-terra.
Configuration
config/experiments.codezen.yaml — 8 cells, repetitions: 3.
Task axes
verification-heavy (12 tasks) as the head-to-head, quick (23) as the control. 2 tasks overlap, so 33 distinct.
Job prefix
codezen → jobs/codezen-<cell>-<task>/.

Why these two axes

verification-heavy is the only axis both toolkits claim, which makes it the only fair head-to-head. SDD claims it through sdd-verify; CodeZen claims it through noc-tdd (test-first) and code-review. The axis selects tasks graded on a large test surface, or whose prompt requires the agent to write the tests — exactly where a verification discipline should pay off if it pays off anywhere.

quick is the control. These are cheap tasks where methodology overhead should show up as cost with little gain. A method that helps on verification-heavy and costs nothing on quick is a very different result from one that helps on both, and both are different again from one that only adds tokens.

SDD's home axis is deliberately not run. spec-dense is where SDD makes its strongest claim and CodeZen makes none, so including it would measure SDD's advantage rather than compare the two. Add it as a follow-up once the head-to-head has a result — --suite spec-dense works with every command below unchanged.

2. The new artefact: codezen-agent-kit

SDD already existed as a repository. CodeZen did not: it ships as a Claude Code / Codex plugin, installed from a marketplace into a plugin cache, and its skills locate their own supporting files through the ${CLAUDE_PLUGIN_ROOT} variable that only a plugin runtime sets. This framework measures a repository by deploying the repository, and there is no plugin runtime inside the container to set that variable.

So the method was reprojected as a checkout at ~/GitRepos/codezen-agent-kit, laid out the way sdd-agent-kit is: CLAUDE.md and AGENTS.md for the instructions, .claude/skills/ and .agents/skills/ for the skills. The projection is mechanical and re-runnable — .codezen-kit/sync-from-plugin.sh — so the diff against upstream stays auditable instead of becoming a hand-maintained fork.

The whole diff against upstream

ChangeWhy it is neededEdits upstream text?
Skills copied into .claude/skills/ and .agents/skills/ The plugin keeps one skills/ and points both runtimes at it through its manifests. A checkout has no manifest to do that. No — byte-identical copies
${CLAUDE_PLUGIN_ROOT}/standards/… → standards/… The only uses of that variable with no fallback. Unset, they resolve to /standards/… and every read fails — silently, because a skill that cannot read its standards still runs. Yes — this is the entire skill-text diff
hooks/ copied to plugin/hooks/ Every other ${CLAUDE_PLUGIN_ROOT} reference is already guarded with a repo-relative elif [[ -f "plugin/hooks/…" ]] that upstream wrote itself. Placing the scripts there makes the unmodified skill text resolve. No
.claude/settings.json added Upstream registers the block-env-edits hook in hooks.json as a plugin path. A checkout declares hooks in project settings instead. No — new file

Full detail, including the per-skill runnability table, is in the kit's own .codezen-kit/UPSTREAM.md.

The kit is published at git@github.com:ChristophMM2108/codezen-agent-kit.git (private), which is what toolkits/codezen/SOURCE records — a remote URL plus GIT_SHA is enough for anyone with access to re-derive the snapshot, which a path under someone's home directory is not.

Two provenance limits, recorded rather than papered over.
  • No upstream commit SHA. ~/GitRepos/codezen-main is not a git repository, so the plugin's declared version: 0.2.0 is the only identifier available. The kit is pinned by SHA (cc50eba852ca516fa5e3a2334aff6873acc30226); the plugin it was cut from is not. Do not imply commit-level provenance in a published result.
  • The hook is declared, not proven. Whether a project-level .claude/settings.json hook fires for a non-interactive claude run inside a container — and whether Codex honours any project-level hook file at all — is unverified. Preflight proves the script is present and executable; it cannot prove it fires. Read that out of the trajectory, do not assume it.

3. Why CodeZen appears twice

CodeZen ships eleven skills. Seven of them need something a benchmark container does not have. Shipping only the full payload would leave a null result unattributable: you could not tell whether the method does not help, or whether most of it never ran. That is the same failure mode already documented for the DFG snapshot in the repository README — files present, preflight green, method inert.

Both conditions are cut from the same snapshot and the same GIT_SHA, using the framework's exclude key. The difference between them is exactly the seven skills above and nothing else — which is what makes the pair interpretable:

What the comparison isolatesRead it from

Do the seven unusable skills cost anything (tokens, distraction, failed invocations)?codezen-full vs codezen-viable

Verified skill counts. generate reports what each condition puts in front of the agent, and the numbers are the design, not an accident: sdd 7 · codezen-full 11 · codezen-viable 4 · baseline 0.

5. Rebuilding the kit from scratch

Only needed if ~/GitRepos/codezen-agent-kit is absent, or to move to a newer plugin version. The toolkit snapshot in this repository is self-contained otherwise.

# 1. Regenerate the kit from a CodeZen plugin checkout
~/GitRepos/codezen-agent-kit/.codezen-kit/sync-from-plugin.sh ~/GitRepos/codezen-main

# 2. Commit it — the framework pins toolkits by commit SHA
cd ~/GitRepos/codezen-agent-kit
git add -A && git commit -m "chore: sync from codezen plugin"

# 3. Re-freeze the snapshot in the bench
cd ~/GitRepos/harbor-methodology-bench
REPO="$HOME/GitRepos/codezen-agent-kit"
rm -rf toolkits/codezen/snapshot && mkdir -p toolkits/codezen/snapshot
git -C "$REPO" rev-parse HEAD              > toolkits/codezen/GIT_SHA
git -C "$REPO" rev-parse --abbrev-ref HEAD > toolkits/codezen/BRANCH
git -C "$REPO" rev-parse --short HEAD      > toolkits/codezen/VERSION
git -C "$REPO" archive HEAD | tar -x -C toolkits/codezen/snapshot

./scripts/freeze-kits.sh --config config/experiments.codezen.yaml

The sync script fails loudly if any unresolvable ${CLAUDE_PLUGIN_ROOT}/standards reference survives, so a silent regression back to the broken-path state is not possible.

7. Budget — read this before starting (retired design)

Costs the 792-trial matrix, not the 108-trial Claude-only path now planned. See the current runbook §8 for the live figures.

33 tasks × 8 cells × 3 attempts = 792 trials. At the repository's own measured figure of roughly 200–800 s and $0.40–$1.30 per trial, that is $320–$1,030 and, serially, on the order of days of wall-clock.

Do not launch all 792 at once. Stage it, and let each stage decide whether the next one is worth paying for.
StageScopeTrialsEst. costDecides
1 --config config/experiments.codezen-probe.yaml --suite verification-heavy --limit 3 --attempts 1 12 $5–15 Does the pipeline hold end to end? Do the CodeZen skills get invoked at all? Claude-only, since one CLI answers that — see the programming-task instructions for the same probe-then-measure shape applied to a task set.
2 --suite verification-heavy --attempts 3 288 $115–375 The head-to-head. This is the result.
3 --suite quick --attempts 3 504 $200–655 The overhead control. Only worth paying for if stage 2 shows an effect.

Cheaper cuts, if stage 2 is still too large: drop to --attempts 1 for a shape check (96 trials — but a single flaky trial then moves a 12-task success rate by 8 points, so it is not reportable), or halve the matrix with a Claude-only run.

Stage 1 is the one with the highest information-per-dollar. The most likely outcome of this whole experiment is zero adherence — CodeZen's skills gate themselves on being asked, and Harbor hands the agent a bare task prompt with no instruction to use a method. 12 trials tell you that before you spend $375 finding out.

8. Reading the result honestly

The framework separates two questions and so should the write-up: was the methodology available (preflight proves it, in-container) and did the agent use it (report.py adherence, read from the trajectory). A passing preflight with zero adherence is a finding about the toolkit, not a broken experiment.

ObservationWhat it meansWhat it does not mean
Skills Used = 0 across every CodeZen cell Nothing in the task prompt prompted a skill, and CodeZen's skills gate on being invoked. A finding about the toolkit's trigger conditions. That the skills were absent — preflight proved they were registered.
Config Referenced = 0 for claude-code The agent never named CLAUDE.md in its trajectory. That it never received it. Claude Code loads project memory silently into its system prompt.
codezen-full ≈ codezen-viable The seven unusable skills cost nothing measurable — they are dead weight, not a drag. That they work.
codezen-full < codezen-viable The unusable skills actively cost something: tokens in the registry, or an agent trying tdd, hitting the Docker pre-flight, and burning budget. Anything about the method itself — that is the viable vs baseline comparison.
Any CodeZen cell beats sdd On verification-heavy tasks, with 3 attempts, for these models. That CodeZen is the better method generally — spec-dense, SDD's home axis, was not run.

Confounds to state in any write-up

  • Skill-count asymmetry. 7 (SDD) vs 11 or 4 (CodeZen). Not matched, and not matchable without editing one of the toolkits.
  • Hook asymmetry. SDD ships no hooks; CodeZen ships one, whose firing is unproven (§2).
  • Repository bulk. SDD's snapshot brings docs/, tests/, tools/, scripts/, kits/; CodeZen's brings standards/ and plugin/. Both put non-method files in the agent's working directory. The repository README's include/exclude scenarios B and C are how you subtract that, if it turns out to matter.
  • CodeZen was adapted; SDD was not. SDD was built as a repository. CodeZen was reprojected into one, and although the diff is one rewrite, the comparison is between a native kit and an adapted plugin.
  • No upstream SHA for CodeZen (§2).

9. Housekeeping

Preflight leaves one tagged image per (condition × task) — harbor-methodology-bench-preflight:<condition>-<task>, so 132 of them for the full 33-task set. They share layers with the task base images, so each costs one thin layer; clear them with docker image prune when convenient.

generate --force replaces only the selected variants, leaving earlier selections in place under generated/. They cannot join a run — the runner resolves its task list from the selection, not from the directory — but rm -rf generated/ is how you start clean.
