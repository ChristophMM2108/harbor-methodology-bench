Programming-task experiments: probe, then measure

A 3-task probe that answers is this worth paying for, then a 16-task measurement split into two independent halves so Codex can be run later, or never. Four conditions throughout. Everything below was executed against this repository except the runs themselves, which spend model tokens.

What the measurement gives up to cost 96 trials

Two cuts against the full 8-cell, 3-attempt matrix, which would have been 384 trials:

CutCostsWhy it was the right cut
3 attempts → 2 A per-cell standard error across attempts. Two observations barely constrain a variance. With 16 tasks the replication unit can be the task — 32 observations per cell — and condition differences are then tested by paired comparison across tasks, which is where the statistical power actually is.
codezen-full dropped from the measurement The codezen-full vs codezen-viable comparison, which prices CodeZen's seven container-unusable skills. The cheapest of the four comparisons to lose: the probe runs all four conditions, so it samples this one on three tasks before you commit to anything.
Tasks were deliberately not cut. 12 tasks × 3 attempts is also 96 trials, and it is the weaker design. For detecting a difference between conditions, task-to-task variance dominates attempt-to-attempt variance, so breadth buys more than depth at a fixed budget — and trimming back to 12 would have dropped both underspecified tasks, the axis both toolkits claim (§2).

Why Codex is a separate run rather than three more cells

B1 and B2 draw disjoint cells from the matrix config/experiments.codezen.yaml declares — B1 the claude-* cells, B2 the codex-* ones, never both. Splitting them buys three things:

  • Codex is optional. Its quota has failed before (§3). Running B1 alone produces a complete, publishable Claude-only result rather than a half-finished matrix.
  • The Codex quota stops being a scheduling risk. Run B2 whenever the quota is confirmed — a week later is fine. Nothing about B1 needs re-running.
  • The two still aggregate into one report. Cell ids carry the agent name (claude-baseline, codex-baseline), so both runs share the job prefix prog16 without colliding, and one --pattern "prog16-*" folds them together whenever B2 lands.
prog16-claude-baseline-build-cython-ext     # B1 writes these
prog16-claude-sdd-build-cython-ext
prog16-codex-baseline-build-cython-ext      # B2 writes these, later
prog16-codex-sdd-build-cython-ext
The four configurations declare identical conditions. Same toolkits:, same snapshots, same exclude lists, same skill_sources — only the matrix and repetitions differ. That equality is what makes A's finding evidence about the conditions B measures, and B1 and B2 comparable to each other. It is asserted mechanically rather than promised in a comment: 
uv run pytest tests/test_configs.py -q          # 7 passed
tests/test_configs.py fails if any CodeZen config's conditions drift, if the two agent halves stop drawing disjoint cells from the full matrix, if they stop exercising the same conditions as each other, or if the probe task file stops being a subset of the 16-task set. Verified to fail on an injected divergence, not merely to pass today.

The four conditions are baseline, sdd, codezen-full and codezen-viable. See the CodeZen runbook for why CodeZen appears twice, what the pair isolates, and how a plugin-shipped methodology was reprojected as a repository so it could be measured at all.

2. Why these tasks

"Programming task" means [metadata].category of software-engineering or debugging — the tightest reading the benchmark's own metadata supports. file-operations and data-processing tasks are excluded even where they involve writing code, so the set says one thing.

The trap this selection avoids. The benchmark's most impressive-looking hard tasks pair an enormous expert estimate with a tiny agent budget: gpt2-codegolf is a 2400-minute human task with a 15-minute agent budget; write-compressor is 1440 against 15. Every condition floors at reward 0 there, and a floor measures nothing about a methodology. Complexity was therefore selected with budget headroom, not on expert estimate alone.

Why the four new tasks are these four

At 12 tasks the set had no underspecified task at all — an axis both toolkits explicitly claim: SDD through sdd-clarify, CodeZen through brainstorm. A methodology whose pitch is "surface ambiguity before implementing" was going to be measured on a set where nothing was ambiguous. polyglot-rust-c and sqlite-db-truncate close that gap. torch-tensor-parallelism pairs with the pipeline-parallelism task already present, and build-pmars gives environment-engineering a second task so the axis does not rest on one.

kv-store-grpc is the in-set control: the one quick task, where methodology overhead should show up as cost with little gain.

The three probe tasks were picked to exercise one distinct skill path each, so a single 12-trial run touches all of them: circuit-fibsqrt builds from scratch against a 13 kB test surface, fix-ocaml-gc requires root-causing before changing code the agent did not write, and schemelike-metacircular-eval is a long-horizon build with the largest test surface in the set. All three carry a 40–60 minute agent budget, which is the headroom a methodology needs in order to be able to pay for itself.

Remaining thinness, stated up front. Only torch-pipeline-parallelism carries spec-dense, which is SDD's strongest claim. That is a property of the benchmark's programming tasks rather than of this selection — the programming categories contain few spec-dense prompts. If the comparison needs SDD's home axis, run --suite spec-dense as a separate experiment rather than stretching this one.

5. The decision gate between A and B

Read A's report before running B1. Four outcomes, four different next moves:

What A showsWhat it meansDo this
Non-zero Skills Used in any CodeZen or SDD cell The methodologies are actually engaging with the task. B1 will measure something. Run B1 as specified.
Skills Used = 0 everywhere, but rewards differ between conditions The instruction files are having an effect without any skill being named — plausible, since Claude Code loads CLAUDE.md silently. Run B1, and treat adherence telemetry as uninformative rather than as evidence of no effect.
Skills Used = 0 and rewards indistinguishable across all four conditions Nothing in a bare Harbor task prompt triggers either methodology. B1 would spend 96 trials confirming a null. Do not run B1 as-is. Fix the trigger first — see below.
Every condition scores 0 on a task Floor effect: that task is too hard for its budget, exactly what the selection tried to avoid. Drop that task from config/tasks-programming.txt before running B1.
The most likely outcome is the third one. Both toolkits gate themselves on being asked: SDD's own CLAUDE.md says to use its skills "for substantial feature development", and CodeZen's skills are user-invocable. Harbor hands the agent a bare task prompt with no instruction to use a method. If A comes back with zero adherence across the board, that is a real finding about the toolkits — and the honest response is to report it, not to spend hundreds of dollars restating it at higher confidence.

--attempts 2 is not optional here. The repetitions: 2 in the configuration file is documentary — it records the intended design and nothing reads it at run time. The runner's real count comes from --attempts, and its default is 1. Omit the flag and you get 48 trials rather than 96, with no warning that the design was not honoured.

Preflight is the step to run before walking away: it builds every image and asserts every condition without spending a single model token. Doing it up front turns a mid-run failure into a five-minute fix.

In zsh, do not build these command lines from shell variables. zsh does not word-split unquoted parameter expansions, so CFG="--config …"; cmd $CFG arrives as one argument and the CLI rejects it with No such option. Use ${=CFG}, write the flags out as above, or use bash. The scripts themselves are sh/bash and are unaffected.

Then re-run the same report command. Because both halves wrote under the prog16 prefix, one pattern now spans all eight cells and the report becomes the full cross-CLI comparison:

python3 scripts/report.py --pattern "prog16-*" \

Want both halves in one go instead? config/experiments.codezen.yaml declares all eight cells — both agents, and codezen-full as well — and takes the same task file. At --attempts 2 that is 256 trials; at --attempts 3, 384. The split exists so Codex can be deferred and the trial count held down, not because the combined matrix is unavailable.

The ceiling column is the sum of the tasks' own [agent].timeout_sec across every cell and attempt — the worst case where every trial runs until its budget expires. Real trials usually finish well short of it, so treat it as an upper bound on wall-clock, not a forecast. The 16-task set totals 460 agent-minutes per cell-pass.

On cost: the repository's own measured figure is $0.40–$1.30 per trial, but that was on a mixed, cheaper task set. These tasks carry 15–60 minute budgets, so plan at $1–3 per trial.

9. Reading the result honestly

The framework keeps two questions apart, and so should the write-up: was the methodology available — preflight proves it, from inside the container — and did the agent use it — report.py adherence, read from the trajectory. A passing preflight with zero adherence is a finding about the toolkit, not a broken experiment.

ComparisonIsolates
sdd vs baselineDoes SDD help on complex programming work?
codezen-viable vs baselineDoes CodeZen's method help?
codezen-full vs codezen-viableDo CodeZen's seven container-unusable skills cost anything — tokens, distraction, budget burned on a failed tdd pre-flight? Available from the probe only (3 tasks, 1 attempt): the measurement drops codezen-full to hold the trial count at 96. Treat it as a signal, not a result.
codezen-viable vs sddDo the two methods differ from each other?
Any condition on kv-store-grpc vs the same condition on the hard tasksFixed overhead: what the methodology costs where it cannot help.
The two underspecified tasks vs the restWhether "surface ambiguity before implementing" — SDD's sdd-clarify, CodeZen's brainstorm — pays anywhere.
B1 vs B2, condition by conditionWhether a methodology effect is a property of the method or of one CLI. Only available once B2 has run.

Confounds to state in any write-up

  • Skill counts are not matched — 7 (SDD) vs 11 or 4 (CodeZen). Not matchable without editing a toolkit.
  • CodeZen was adapted; SDD was not. SDD was built as a repository. CodeZen ships as a plugin and was reprojected into one. The diff is a single rewrite, but the comparison is still native-kit versus adapted-plugin.
  • CodeZen has no upstream commit SHA — the plugin checkout it was cut from is not a git repository, so version: 0.2.0 is the only identifier. The kit itself is SHA-pinned.
  • CodeZen's hook is declared, not proven. Whether a project-level .claude/settings.json hook fires for a non-interactive run inside a container is untested. Read it from the trajectory.
  • Repository bulk differs. SDD's snapshot brings docs/, tests/, tools/, scripts/; CodeZen's brings standards/ and plugin/. Both put non-method files in the agent's working directory.
  • One spec-dense task, so SDD's strongest claim is barely represented (§2).
  • Two attempts, not three. Below the repository README's stated minimum for a reportable mean. Report condition differences as paired comparisons across the 16 tasks — 32 observations per cell — rather than as a per-cell success rate with a standard error over attempts, which two observations cannot support.
  • The measurement compares SDD-as-shipped against a curated CodeZen subset. codezen-viable is 4 of CodeZen's 11 skills, chosen for being container-runnable; SDD's 7 are all shipped and all runnable. That asymmetry favours CodeZen on focus and disfavours it on breadth, and it is the direct consequence of dropping codezen-full from the measurement.
  • If B2 is skipped, the result is Claude-only — and CodeZen ships a .codex-plugin/ whose Codex support then goes untested.

10. Housekeeping

Preflight leaves one tagged image per condition × task — harbor-methodology-bench-preflight:<condition>-<task>, so 64 for the full 16-task set. They share layers with the task base images, so each costs one thin layer; clear them with docker image prune when convenient.

generate --force replaces only the selected variants and leaves earlier selections in place under generated/. They cannot join a run — the runner resolves its task list from the selection, not from the directory — but rm -rf generated/ is how to start clean.

Both runners skip cells that already have a finished result, so an interrupted run resumes by re-issuing the same command. A job directory whose result.json has finished_at: null or cancelled trials counts as unfinished and is re-run — an interrupted cell is never silently dropped from the matrix. This is also why B2 cannot disturb B1: different cell ids mean different job directories.
