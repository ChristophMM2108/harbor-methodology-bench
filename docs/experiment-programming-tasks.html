A 3-task probe that answers is this worth paying for, and a 12-task experiment that produces the result. Same four conditions, same eight cells, same commands — only the task file, the job prefix and the attempt count change. Everything below was executed against this repository except the two runs themselves, which spend model tokens.

Why the probe is Claude Code only. Its question is narrow: do either toolkit's skills fire at all when the agent is handed a bare Harbor task prompt? One CLI answers that at half the trial count. The cost is that nothing is learned about Codex — including CodeZen's own Codex support, which its .codex-plugin/ and codex-hooks.json exist to provide. Both Codex cells return in experiment B.
A is a strict subset of B, by design. The three probe tasks are the first three lines of the 12-task file. The job prefixes differ (probe3 / prog12), so B never collides with A's job directories and both results survive independently — but they are results about the same three tasks, so a contradiction between them is a signal about run-to-run variance rather than about the tasks.

2. Why these tasks

"Programming task" is taken to mean [metadata].category of software-engineering or debugging — the tightest reading the benchmark's own metadata supports. file-operations and data-processing tasks are excluded even where they involve writing code, so the set means one thing.

The trap this selection avoids. The benchmark's most impressive-looking hard tasks pair an enormous expert estimate with a tiny agent budget: gpt2-codegolf is a 2400-minute human task with a 15-minute agent budget; write-compressor is 1440 against 15. Every condition floors at reward 0 there, and a floor measures nothing about a methodology. Complexity was therefore selected with budget headroom, not on expert estimate alone.

The three probe tasks were picked to exercise one distinct skill path each, so a single 12-trial run touches all of them: circuit-fibsqrt builds from scratch against a 13 kB test surface, fix-ocaml-gc requires root-causing before changing code the agent did not write, and schemelike-metacircular-eval is a long-horizon build with the largest test surface in the set. All three carry a 40–60 minute agent budget, which is the headroom a methodology needs in order to be able to pay for itself.

kv-store-grpc is the in-set control: the one quick task, where methodology overhead should show up as cost with little gain.

Known thinness, stated up front. Only torch-pipeline-parallelism carries spec-dense, which is SDD's strongest claim. That is a property of the benchmark's programming tasks, not of this selection — the programming categories simply contain few spec-dense prompts. If the comparison needs SDD's home axis, run --suite spec-dense as a third experiment rather than stretching this one.

5. The decision gate between A and B

Read A's report before running B. Three outcomes, three different next moves:

What A showsWhat it meansDo this
Non-zero Skills Used in any CodeZen or SDD cell The methodologies are actually engaging with the task. B will measure something. Run B as specified.
Skills Used = 0 everywhere, but rewards differ between conditions The instruction files are having an effect without any skill being named — plausible, since Claude Code loads CLAUDE.md silently. Run B, and treat adherence telemetry as uninformative rather than as evidence of no effect.
Skills Used = 0 and rewards indistinguishable across all four conditions Nothing in a bare Harbor task prompt triggers either methodology. B would spend 288 trials confirming a null. Do not run B as-is. Fix the trigger first — see below.
Every condition scores 0 on a task Floor effect: that task is too hard for the budget, exactly what the selection tried to avoid. Drop that task from config/tasks-programming.txt before running B.
The most likely outcome is the third one. Both toolkits gate themselves on being asked: SDD's own CLAUDE.md says to use its skills "for substantial feature development", and CodeZen's skills are user-invocable. Harbor hands the agent a bare task prompt with no instruction to use a method. If A comes back with zero adherence across the board, that is a real finding about the toolkits — and the honest response is to say so, not to spend $300 on 288 trials restating it at higher confidence.

In zsh, quote or splat those variables. zsh does not word-split unquoted parameter expansions, so $CFG arrives as one argument and the CLI rejects it with No such option. Use ${=CFG}, or run the commands with the flags written out, or use bash. The scripts themselves are sh/bash and are unaffected — this only bites when you build the command line from shell variables interactively.

Preflight is the step to run before walking away: it builds every image and asserts every condition without spending a single model token. Doing it up front turns a mid-run failure into a five-minute fix.

7. Budget and wall-clock

TrialsAgent-budget ceilingPlanning cost

The ceiling column is the sum of the tasks' own [agent].timeout_sec across every cell and attempt — the worst case where every trial runs until its budget expires. Real trials usually finish well short of it, so treat it as an upper bound on wall-clock, not a forecast.

On cost: the repository's own measured figure is $0.40–$1.30 per trial, but that was on a mixed, cheaper task set. These tasks carry 15–60 minute budgets, so plan at $1–3 per trial.

8. Reading the result honestly

The framework keeps two questions apart, and so should the write-up: was the methodology available — preflight proves it, from inside the container — and did the agent use it — report.py adherence, read from the trajectory. A passing preflight with zero adherence is a finding about the toolkit, not a broken experiment.

ComparisonIsolates
sdd vs baselineDoes SDD help on complex programming work?
codezen-viable vs baselineDoes CodeZen's method help?
codezen-full vs codezen-viableDo CodeZen's seven container-unusable skills cost anything — tokens, distraction, budget burned on a failed tdd pre-flight?
codezen-viable vs sddDo the two methods differ from each other?
Any condition on kv-store-grpc vs the same condition on the hard tasksFixed overhead: what the methodology costs where it cannot help.

Confounds to state in any write-up

  • Skill counts are not matched — 7 (SDD) vs 11 or 4 (CodeZen). Not matchable without editing a toolkit.
  • CodeZen was adapted; SDD was not. SDD was built as a repository. CodeZen ships as a plugin and was reprojected into one. The diff is a single rewrite, but the comparison is still native-kit versus adapted-plugin.
  • CodeZen has no upstream commit SHA — the plugin checkout it was cut from is not a git repository, so version: 0.2.0 is the only identifier. The kit itself is SHA-pinned.
  • CodeZen's hook is declared, not proven. Whether a project-level .claude/settings.json hook fires for a non-interactive run inside a container is untested. Read it from the trajectory.
  • Repository bulk differs. SDD's snapshot brings docs/, tests/, tools/, scripts/; CodeZen's brings standards/ and plugin/. Both put non-method files in the agent's working directory.
  • One spec-dense task, so SDD's strongest claim is barely represented (§2).

9. Housekeeping

Preflight leaves one tagged image per condition × task — harbor-methodology-bench-preflight:<condition>-<task>, so 48 for the full 12-task set. They share layers with the task base images, so each costs one thin layer; clear them with docker image prune when convenient.

generate --force replaces only the selected variants and leaves earlier selections in place under generated/. They cannot join a run — the runner resolves its task list from the selection, not from the directory — but rm -rf generated/ is how to start clean.

Both runners skip cells that already have a finished result, so an interrupted run resumes by re-issuing the same command. A job directory whose result.json has finished_at: null or cancelled trials counts as unfinished and is re-run — an interrupted cell is never silently dropped from the matrix.
