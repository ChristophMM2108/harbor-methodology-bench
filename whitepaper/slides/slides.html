The Cost of Process

The question

Does a repository’s agent configuration make the agent better?

Two published coding-agent toolkits, frozen at a Git SHA and deployed as shipped — CLAUDE.md, AGENTS.md, a skills directory, the surrounding docs — against a bare agent on the same tasks.

The trap: the naive version measures nothing

Harbor transfers only instruction.md, tests/ and solution/ into the container. A CLAUDE.md placed next to task.toml never reaches the agent. An experiment built that way returns a clean null and no way to tell it from an absent condition.

  • available? hmb preflight — an assertion made from inside the running container, before any trial. All 78 task variants passed.
  • used? hmb analysis — adherence read from the agent’s own trajectory: Skill calls, sub-agent spawns, shell buckets.

Keeping those two questions apart is what makes slide 12 possible — and slide 12 changes what every other result is a result about.

Why Terminal-Bench 2.0 is the right substrate…

The reward is a verifier, not a judge. A task passes when its own test suite passes. No model grades style or process, so a methodology can only score by changing the artefact on disk — which removes the most common way a process evaluation flatters itself.

…and where it fights back

Every task declares a wall-clock budget, and Harbor enforces it. That single fact turns out to be the dominant mechanism in the whole dataset.

Tasks are self-contained and fully specified. Specification processes are motivated by the opposite situation, so this is the regime in which one has least to add.

Availability is proven, not assumed

The generated Dockerfile is byte-identical across every condition of a task, and the baseline working directory is proven byte-identical to the untouched base image. No build-path difference can be mistaken for a methodology effect.

What comes out

trials.csv · tests.csv · steps.csv · tool_calls.csv · adherence.csv · condition summaries. One row per trial, one row per verifier test, one row per agent step.

The clock is inside the loop

Harbor kills the container at the wall. A kill is right-censoring: the trial stopped before the event of interest. Harbor still records what the verifier scored on the workspace it killed — which slide 10 turns into the cheapest available fix.

Where these runs sit

Five runs, three overshoots

Each run’s design was chosen to repair the previous run’s defect. The repair overshot every time — and that is the most transferable lesson in the experiment.

probe32026-08-26 · 12 trials · $24.94 Gate: is adherence non-zero? Its predicted null did not happen, so the gate opened.
prog162026-08-27 · 16 tasks · $75.49 Selected for human-expert difficulty. Null on outcome, measured cost — and a ceiling that made the null uninformative.
screen2026-08-31 · 83 candidates One bare baseline trial per candidate, plus oracle and nop. 16 kept · 64 excluded · 3 undecided.
suite96 trials · $114.90 The 16 the bare agent failed → floor: 7 of 16 failed by everything.
ceiling60 trials · $86.46 10 of the 57 it rejected → ceiling by construction; run as a cost probe.

Three screens, three overshoots

Selecting for human-expert difficulty produced a ceiling (baseline 81 %). Screening for “the bare agent fails” produced a floor (37.5 %). The rejected set is a ceiling by construction (90 %). No screen in this sequence landed in the discriminating band.

The two runs reported here are the screen’s two sides, pooled into 156 trials · 26 tasks · $201.37. Pooling is what makes the length analysis on slide 13 possible — and it is also that analysis’s main confound, because run membership and task length are correlated but not aligned.

Direct evidence the one-trial rule misclassifies both ways: make-mips-interpreter was excluded as “the bare agent already passes it” — and baseline then failed both of its attempts in the run that used it.

Before any number

Two reporting conventions decide the answer

Neither is cosmetic. On the ceiling population the censoring convention alone moves CodeZen across 27.9 points and three ranks.

The primary convention here is censored, because the agent was stopped, not beaten. Both alternatives are reported wherever they change something. Six of CodeZen’s 20 ceiling trials were killed, against baseline’s one — which is why the convention has this much leverage on one condition and almost none on the others.

And a third option beats all three

Harbor already recorded what the verifier scored on the workspace it killed. 7 of the 23 kills across both runs scored reward 1.0. Grading at the kill turns a lost observation into a measured one and costs no model tokens — slide 10.

2 · what “the task passed” means at two attempts
  • pass-at-2at least one of the two attempts passed. The capability reading.
  • pass-bothboth attempts passed. The reliability reading.

They disagree about whether SDD regressed zero tasks or three. Both are quoted wherever they diverge.

Statistics, and the power behind every null
  • Every task ran in every condition, so tests are paired: exact McNemar on binary outcomes, Wilcoxon signed-rank on per-task means, Wilson intervals on proportions, two-sided Spearman for length.
  • 80 % power at α = 0.05 needs |ρ| ≥ 0.53 at n = 26 and ≥ 0.79 at n = 10. Anything below that is “not resolved”, never “absent”.
  • p = 0.002 is the minimum attainable value for a two-sided Wilcoxon at n = 10. It means the effect is present on every task — not that it is large.
Results I · outcome

The null — and it is the weakest half of the paper

Every McNemar test is non-significant. 18 of 26 tasks are concordant. Effective sample size per paired outcome test is 1–5. This is an underpowered, internally inconsistent null, not a demonstrated absence.

Outcome by condition, at three resolutions — both runs

On suite, the coarse and fine metrics do not rank the conditions the same way

Success rate puts CodeZen first by 11 points — on a difference of two trials. Partial credit puts baseline first by 0.017 — but exactly one trial in the 156 has no per-test record, and scoring that failure 0 makes it 0.517 against 0.516, a tie. Test-level rate reproduces neither: 60.0 % against 59.8 %.

The pooled test count does not buy power

357 suite test rows are not 357 independent observations — they cluster in 16 tasks, two of which supply 30 %. Design effects 5.7–7.4, effective n 16–20. Clustered intervals run 42–48 points wide where binomial ones on the same counts run 17–18.

The one fine-grained signal worth carrying

SDD satisfies 0.82–0.83× of each verifier’s tests — the same shortfall, independently, on both populations. It never reaches significance (p = 0.125 at n = 10). The consistency across two disjoint task sets is more interesting than either p-value, and slide 12 supplies a mechanism.

95 % Wilson intervals on the success column: [13, 43] [20, 55] [12, 42] on suite; [69, 97] [69, 99] [55, 91] on ceiling — each contains every other.  Exact McNemar under pass-at-2: p = 0.625 (CodeZen), p = 1.000 (SDD) on suite; p = 1.000 for both on ceiling.

Why neither population could have shown an outcome effect

A one-trial screen is monotone in the wrong quantity

The rule keeps exactly the wrong tasks

It keeps hopeless tasks with certainty and discards half of the ideally discriminating ones. One trial cannot distinguish always fails — a floor task that carries no information — from sometimes fails, the only kind of task that separates two conditions.

  • Across ~60,000 agent trajectories on SWE-Bench-Verified, single-run performance estimates vary substantially between runs, including at temperature zero. A one-trial screen samples run-to-run noise as much as task difficulty.
  • Direct evidence of misclassification in both directions is in the runs themselves: make-mips-interpreter was excluded as already-passing, and baseline then failed both attempts.

The fix, and its price

A two-sided rule on the baseline pass rate: keep a task when 1 or 2 of 3 baseline trials pass. Three baseline trials per candidate instead of one — roughly 2× the screen’s cost, and the only change that materially improves outcome power.

The uncomfortable possibility, stated plainly

The discriminating band may be narrow and unstable — in which case no affordable screen produces a well-powered outcome comparison, and cost and conformance should be promoted to primary endpoints with outcome demoted to secondary. Both runs are consistent with that. Neither establishes it.

What the price buys

0.96–1.00× the partial credit. Level, once the one baseline trial with no per-test record is counted as the failure it was. The 3.11× is the number that bites, because the methodology cannot tell in advance which kind of task it is on.

The mechanism is delegation, and it is measured

2.6 sub-agents per trial against baseline’s 0.04. 84 spawns across CodeZen’s 32 suite trials against 1 for baseline and 0 for SDD. Each inherits prompt context and produces its own thinking and output tokens.

Three objections, closed

The smaller run is the stronger evidence. 10 of 10 on four separate metrics beats 12 of 16: no task where the effect is absent, no runaway trial carrying the mean.

SDD’s cost is not the story. 1.10–1.14× is indistinguishable from baseline in both runs. Its shortfall is in what it satisfied, not what it spent.

The chain, measured rather than inferred

1. CodeZen delegates — 2.55 sub-agents per trial against baseline’s 0.05 — and reviews after implementing.  2. That work is real and takes wall-clock, so budget consumption rises 1.90×.  3. On tasks whose budget is tight relative to their size, the extra consumption crosses the wall and Harbor kills the agent.  4. Sometimes the work was already done. Sometimes it was not.

The single most illuminating trajectory in the dataset

The post-completion trap

headless-terminal under CodeZen. Not a story about difficulty — a story about an agent with no termination gate.

65.6 s — green CodeZen runs the tests — the responsible thing — and they pass. Reward 1.0 is on disk. the wall Harbor kills the container. Both attempts recorded as censored — despite scoring reward 1.0.

834 seconds of ceremony — docstrings, defensive assertions and stylistic tweaks across nine sub-agents, at $2.21 and $2.79: 8.1× and 14.1× baseline.

baseline, same task finished in 144.5 s and 114.1 s for $0.27 and $0.20, with zero recognised test invocations on either attempt: it edited the code, stopped, and was right anyway.

The architectural lesson

An autonomous agent under a real time or compute budget needs an explicit exit condition. When verification already succeeds, procedural review skills must be suppressed, or gated behind a strict time-remaining threshold.

In human engineering, thoroughness and peer review are virtues. In an agent with a fixed clock and no termination gate, thoroughness is a failure mode.

The same machinery, on work that was not already done

Baseline meets a hard barrier — a missing shared library, a convergence problem, an obscure binary format — tries a few commands and stops inside about 20 steps and $0.68.

CodeZen treats failure as a signal to invoke process: noc-tdd to write tests, code-review to inspect non-working code, noc-fix to attempt repairs. Because every sub-agent runs the same model, they share the parent’s blind spots and cannot conjure domain knowledge the base model lacks. On filter-js-from-html that loop reached 100 % of budget on both attempts at a 16.0× cost ratio, with zero passing tests.

Shell commands are bucketed by pattern rather than parsed, so “verification commands” is a comparison between conditions on one corpus, not an absolute count.

CodeZen verifies far more, and it does not help

3.56 verification commands per trial against baseline’s 0.56 in suite — a 6.3× increase, p = 0.046 — and it wrote a dedicated test file in 34.4 % of trials against 9.4 %. Partial credit still came out 0.96× baseline.

A hypothesis for why — proposed, not measured

The verifier is an external oracle the agent cannot see. When an agent writes its own tests it tests against its own reading of the problem: a misread edge case gets encoded in a test, runs green, and is believed. Ungrounded test-driven development produces false confidence. The instrument that would settle it: log a “mock misalignment” event whenever the agent’s own suite passes and the verifier does not.

SDD points the wrong way on the one behaviour that matters

Near-invisible otherwise — steps 1.13×, tool calls 1.07×, wall-clock 0.99×, zero sub-agents — but on ceiling it ran zero recognised verification commands across 20 trials, against baseline’s 0.30 and CodeZen’s 1.65. For a toolkit shipping an sdd-verify skill, that lines up with the partial-credit shortfall: it satisfied 68.5 % of verifier tests against baseline’s 90.7 % and checked its work less than the bare agent.

Results V · a claim we had to walk back

Longer tasks do not make process more valuable

A real effect sharpens with the instrument. This one dissolves.

80 % power at n = 26 needs |ρ| ≥ 0.53, so every row above is “not resolved”, not “absent”. A weak positive lean exists only in the coarsest metric. That is the signature of noise in a coarse metric.

The most pointed result in the dataset

This is not “we could not find the effect where we looked”. It is “the toolkit looked in the same place, acted on the same belief, and the belief did not pay”.

SDD invokes its chain 2.2× more often on long-horizon tasks (ρ = +0.379 against log expert time, p = 0.056). It gates itself on perceived task size and engages exactly where the hypothesis says it should pay off — and posts the largest partial-credit deficit anywhere in the data on precisely those tasks: −0.182 on long-horizon against −0.080 on short.

Toolkit invocation against task horizon

Two limits on this analysis

The pooled sample mixes two populations selected on baseline outcome, so run membership dominates baseline pass rate more than long-horizon status does. Long-horizon tasks split 5 / 5 between the runs, so the confound is not aligned with the predictor — but it is not orthogonal either.

And the range is not the range the hypothesis is about. These tasks top out at a day of expert time in a single autonomous session with a fully specified instruction. The hypothesis concerns multi-session work with ambiguous requirements and a human in the loop.

The strongest cross-run claim, adjudicated

“Just retry more”: plausible, not proven

The sharpest operational claim from the independent review is that a fixed budget is better spent on more independent attempts with the bare agent than on a methodology. The argument is arithmetic — and the arithmetic rests on an assumption this data contradicts.

P(at least one of k passes) = 1 − (1 − p)k

…which assumes every attempt on every task is an exchangeable draw from one common Bernoulli rate. On suite that gives 59 % against CodeZen’s 36 % for the same money, and the conclusion drawn was that repeated sampling strictly dominates process.

The two-attempt design tests that assumption directly — and it leans the wrong way in 5 of 6 cells

Observed pass-at-2 falls below the independence prediction: suite baseline 0.375 against 0.438; SDD 0.313 against 0.390; CodeZen 0.500 against 0.569. No single cell rejects homogeneity at n = 10–16 (χ² gives p = 0.16 to 0.57), but the sign is consistent and the mechanism is not in doubt: ten of sixteen suite tasks were failed by baseline on both attempts, and retries cannot rescue a task that is dead.

homogeneous denies task heterogeneity — the optimistic bound. plug-in takes two-attempt per-task estimates at face value — the pessimistic bound. beta-binomial fits the heterogeneity by maximum likelihood.

Bounded, not settled

At 6.2 baseline attempts for the price of CodeZen’s two, the retry strategy reaches somewhere between 37 % and 83 % against CodeZen’s measured 50 %. The homogeneous model favours retries by 33 points, the beta-binomial by 8.6 — and the plug-in model favours CodeZen by 12.8.

The sign changes with the estimator, so “repeated sampling strictly dominates” is not established. It remains the most plausible reading — two of three estimators favour retries, and the dissenting one has the clearest upward bias in its assumptions — but plausible is the correct word.

Best-of-N curves under the three estimators

On ceiling no estimator is needed

Baseline already passes 89.5 % of graded trials, so extra attempts buy almost nothing and the overhead is a pure loss rather than a trade. All three estimators put baseline retries at or above CodeZen’s 90 %.

None of this is a measurement

Nobody has run baseline at 3× the attempts and compared. That experiment needs no new infrastructure, is the comparison an operator actually faces, and would replace a three-estimator range with a number. It is the highest-value cheap experiment left.

Conclusion

What is settled, what is not, and what to change

Supported
  • CodeZen costs 1.71× on work that completes and 3.11× on work that does not, for 0.96–1.00× the partial credit. Significant on two independent populations, with delegation as the measured mechanism.
  • Process converts into censoring risk: 1.90× budget consumption, 25 % of CodeZen trials killed by the clock against 9.6 %.
  • Methodology can regress a solved task, and can make a solved task less reliable.
  • 71 % of toolkit trials invoked no toolkit skill. Availability was total.
  • Human-expert difficulty does not predict agent difficulty (ρ = −0.078, p = 0.70).
  • The one-trial screening rule is unreliable in both directions.
  • The censoring convention is decision-relevant, and 7 of 23 kills discarded a workspace scoring 1.0.
Not supported
  • Any claim about which configuration produces better outcomes. 18 of 26 tasks are concordant; effective n is 1–5.
  • That SDD’s partial-credit shortfall is real rather than noise (p = 0.125 at n = 10) — though it appears at the same magnitude on both populations.
  • Any causal reading of “skill-invoking trials mostly failed”. Selection and effect are inseparable here.
  • That retries beat process at equal spend. The sign changes with the estimator.
  • Anything about the regime methodologies are actually written for: multi-session work with ambiguous requirements and a human in the loop.
The five confounds that actually bind

1. The measured population is not the target population — single-session, self-contained, fully specified. 2. The condition is a repository, not a methodology text. 3. codezen-viable is a curated four-skill subset of eleven. 4. Method availability, not enforcement — the agent was never instructed to follow the process. 5. Concurrency inflates the clock; paired comparisons survive, absolute budget percentages do not.

What to change
  • do firstGrade the workspace at the moment of the kill. 7 of 23 kills scored 1.0 anyway. Costs no model tokens.
  • 2× screen costScreen on baseline pass rate. Keep a task when 1 or 2 of 3 baseline trials pass. The only change that materially improves outcome power.
  • new variableRandomise invocation — mandate the process in half the trials. Breaks the selection/effect confound.
  • cheapRun the equal-budget retry comparison. Replaces a three-estimator range with a measurement.
  • agent designGate procedural skills on state and on time remaining. No delegated review when the tests are already green, or on a small fraction of budget.

The general form of the finding

The result is not that these two toolkits are badly built. It is that a fixed process applied unconditionally is the wrong shape of thing for an agent under a bounded budget.

Autonomous coding methodology is better treated as an adaptive resource-allocation policy than as a universally beneficial fixed process.
