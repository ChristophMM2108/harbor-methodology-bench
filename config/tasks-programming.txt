# Programming task set — 16 tasks
#
# This is the measurement, experiments B1 (Claude) and B2 (Codex). Run the probe
# in config/tasks-programming-probe.txt first — it is a strict subset of this
# file, and its report is the gate on whether spending this one is worth it.
#
# Every task here has [metadata].category of `software-engineering` or
# `debugging`: the tightest reading of "programming task" the benchmark's own
# metadata supports. file-operations and data-processing tasks are excluded even
# where they involve code, so the set says one thing.
#
# Selected for complexity with usable budget headroom, and for spread across the
# kinds of work the two toolkits claim. Rejected on purpose:
#   gpt2-codegolf, write-compressor, make-doom-for-mips  24h / 24h / 8h expert
#                                                        estimate against a 15m
#                                                        agent budget — every
#                                                        condition floors at 0
#   build-pov-ray                                        200-minute budget would
#                                                        dominate wall-clock
#   fix-git, prove-plus-comm, polyglot-c-py              5–20 minute expert
#                                                        estimate; not complex
#   headless-terminal, winning-avg-corewars              match no axis, so
#                                                        nothing predicts whether
#                                                        a methodology should help
#
# The first three are the probe set (config/tasks-programming-probe.txt).
#
#   task                          diff  expert  budget  axes
#   ----------------------------------------------------------------------------
#   circuit-fibsqrt               hard   960m     60m   long-horizon, verification-heavy, greenfield
#   fix-ocaml-gc                  hard  1440m     60m   long-horizon, diagnose-first, modify-existing
#   schemelike-metacircular-eval  med    300m     40m   long-horizon, verification-heavy, greenfield
#   regex-chess                   hard  1440m     60m   long-horizon
#   make-mips-interpreter         hard   480m     30m   long-horizon, greenfield
#   path-tracing                  hard   360m     30m   long-horizon, greenfield
#   path-tracing-reverse          hard   120m     30m   modify-existing
#   torch-pipeline-parallelism    hard   240m     15m   spec-dense, long-horizon, greenfield
#   torch-tensor-parallelism      hard   240m     15m   long-horizon, greenfield
#   polyglot-rust-c               hard   180m     15m   underspecified, greenfield
#   cancel-async-tasks            hard   120m     15m   greenfield
#   build-pmars                   med     90m     15m   diagnose-first, environment-engineering
#   build-cython-ext              med     60m     15m   diagnose-first, modify-existing, environment-engineering
#   sqlite-db-truncate            med     60m     15m   underspecified, diagnose-first, modify-existing
#   custom-memory-heap-crash      med     30m     30m   diagnose-first, modify-existing
#   kv-store-grpc                 med     15m     15m   quick
#
# Axis coverage across the 16:
#   long-horizon 8 · greenfield-algorithmic 8 · diagnose-first 5 ·
#   modify-existing 5 · verification-heavy 2 · underspecified 2 ·
#   environment-engineering 2 · spec-dense 1 · quick 1
#
# kv-store-grpc is the in-set control: the one `quick` task, where methodology
# overhead should show up as cost with little gain.
#
# The four tasks added when this set grew from 12 to 16 were chosen to close its
# largest gap. At 12 tasks the set had *no* `underspecified` task at all, which
# left untested an axis both toolkits explicitly claim — SDD through
# `sdd-clarify`, CodeZen through `brainstorm`. polyglot-rust-c and
# sqlite-db-truncate supply it. torch-tensor-parallelism pairs with the
# pipeline-parallelism task already present, and build-pmars adds a second
# environment-engineering case so that axis rests on more than one task.
#
# Remaining thinness: only torch-pipeline-parallelism carries `spec-dense`, which
# is SDD's strongest claim. That is a property of the benchmark's programming
# tasks rather than of this selection — run `--suite spec-dense` as a separate
# experiment if the comparison needs SDD's home axis.
#
# ---------------------------------------------------------------------------
# Experiment B1 — the measurement, Claude Code. 16 tasks x 3 cells x 2 attempts
# = 96 trials, 48 Harbor invocations. Full write-up:
# docs/experiment-programming-tasks.html §6.
#
#   ./scripts/catalogue.sh          --config config/experiments.codezen-claude.yaml \
    --tasks-file config/tasks-programming.txt --ids-only
#   ./scripts/generate-variants.sh  --config config/experiments.codezen-claude.yaml \
#    --tasks-file config/tasks-programming.txt --force       # 64 variants
#   ./scripts/validate-variants.sh  --config config/experiments.codezen-claude.yaml \
#    --tasks-file config/tasks-programming.txt
#   ./scripts/preflight-variants.sh --config config/experiments.codezen-claude.yaml \
#    --tasks-file config/tasks-programming.txt               # builds 64 images
#   ./scripts/run-pilot-experiment.sh --config config/experiments.codezen-claude.yaml \
#    --tasks-file config/tasks-programming.txt \
#    --job-prefix prog16 --attempts 2 --dry-run              # 48 invocations
#   ./scripts/run-pilot-experiment.sh --config config/experiments.codezen-claude.yaml \
#    --tasks-file config/tasks-programming.txt \
#    --job-prefix prog16 --attempts 2                        # spends tokens
#   python3 scripts/report.py --pattern "prog16-*" \
#    --md-out results/prog16_report.md --json-out results/prog16_summary.json
#
# Experiment B2 — the same measurement, Codex. Optional, and later: every Codex
# trial in an earlier run failed with ApiUsageLimitError before reaching the
# task. Confirm the quota on the cheapest task first, then run the same steps
# against the Codex config. Details: docs/experiment-programming-tasks.html §7.
#
#   ./scripts/run-pilot-experiment.sh --config config/experiments.codezen-codex.yaml \
#     --task kv-store-grpc --job-prefix quotacheck --attempts 1   # canary
#   ./scripts/preflight-variants.sh --config config/experiments.codezen-codex.yaml \
#     --tasks-file config/tasks-programming.txt              # no-op after B1
#   ./scripts/run-pilot-experiment.sh --config config/experiments.codezen-codex.yaml \
#     --tasks-file config/tasks-programming.txt \
#     --job-prefix prog16 --attempts 2
#
# Both halves write under the same `prog16` prefix — cell ids carry the agent
# name — so the one report command above spans B1 alone today and both halves
# once B2 lands.
#
# --attempts 2 is not optional. `repetitions:` in the config file is
# documentary; the runner reads its count from --attempts, whose default is 1.
# Omit the flag and you get 48 trials instead of 96, silently. Both halves must
# use the same count or they are not comparable; tests/test_configs.py asserts
# the configs agree on it.
#

# CLI rejects it with `No such option`. Use ${=CFG}, or bash.
# ---------------------------------------------------------------------------
